# SOLUTION — 21 · Expense Reporting Service

> Reference copy. Do not read this until you have finished, or until you have asked for the solution
> explicitly.

Eight defects. Seven are in `pom.xml` and `application.properties`; the eighth is the Java defect
that the other seven kept hidden.

| # | Symptom | Area |
|---|---|---|
| 1 | `no main manifest attribute` | `spring-boot-maven-plugin` never declared |
| 2 | `Cannot load driver class: org.h2.Driver` | H2 at `test` scope |
| 3 | Starts, then exits `0` with no server | `spring-boot-starter-tomcat` excluded |
| 4 | Every endpoint with a date returns `500` | `jackson-datatype-jsr310` excluded |
| 5 | `/api/meta` returns `500` | `${project.version}` instead of `@project.version@` |
| 6 | `Tests are skipped` | `<skipTests>true</skipTests>` |
| 7 | No test output at all | Surefire `<includes>` does not match the class name |
| 8 | `grandTotal` is always `0` | `BigDecimal.add` result discarded |

---

## Defect 1 — the Spring Boot Maven plugin is not declared

**Where:** `pom.xml`, the `<build><plugins>` section.

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            ...
        </plugin>
    </plugins>
</build>
```

**Root cause:** `mvn package` produces an ordinary library jar — your classes and a manifest with no
`Main-Class`. What makes a Spring Boot application executable is the plugin's `repackage` goal,
which rewrites that jar into an executable archive: dependencies under `BOOT-INF/lib`, your classes
under `BOOT-INF/classes`, the launcher under `org/springframework/boot/loader`, and a manifest with
`Main-Class: org.springframework.boot.loader.launch.JarLauncher` plus
`Start-Class: com.debuglab.expenses.ExpenseApplication`.

Without it you get an 11 KB jar that `java -jar` cannot start. The give-away is the size: a Boot
application jar is tens of megabytes because it carries its dependencies.

**Fix:**

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>
```

No `<version>` is needed — `spring-boot-starter-parent` manages it.

**Why a fresher writes this:** the plugin is generated by start.spring.io, so nobody ever types it.
It gets lost when a POM is hand-written, or when somebody reorganises the `<build>` section, or when
a module is copied from a library project that legitimately does not have it. Everything still
compiles and `mvn test` still passes, so nothing complains until the first deployment.

**How to recognise it in a real project:** `no main manifest attribute` plus a suspiciously small
jar. `unzip -l` and look for `BOOT-INF/`. If it is not there, the repackage step did not run.

## Defect 2 — H2 is declared at `test` scope

**Where:** `pom.xml`.

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>
```

**Root cause:** `test` scope means the dependency is on the compile and run classpath **for tests
only**. It is not packaged into the application jar and is not on the `spring-boot:run` classpath.
Nothing in `src/main` references an H2 class directly — the driver is named in a properties file and
loaded reflectively — so the code compiles perfectly and the mistake survives all the way to
start-up:

```
java.lang.IllegalStateException: Cannot load driver class: org.h2.Driver
```

The diagnostic pattern matters more than the fix: `mvn test` is green, `java -jar` and
`mvn spring-boot:run` both fail. Two classpaths, one declared dependency, different behaviour —
that is a scope problem, essentially every time.

**Fix:**

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>
```

`runtime` is right for a JDBC driver: nothing compiles against it, and it must ship. The same
applies to `mysql-connector-j` and `postgresql`, which is why every other project in this laboratory
declares them that way.

**Why a fresher writes this:** "H2 is the test database, so it goes in test scope" is an entirely
reasonable sentence that happens to be wrong here, because this application uses H2 as its real
database. It is also what happens when a project starts with MySQL, H2 is added for tests, and later
somebody points the development profile at H2 without revisiting the scope.

**How to recognise it in a real project:** anything that works in tests and not when run, or works
in the IDE and not from the jar. `mvn dependency:tree` prints the scope next to every artifact —
read it, do not assume it.

## Defect 3 — the embedded servlet container is excluded

**Where:** `pom.xml`, on `spring-boot-starter-web`.

```xml
<exclusion>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-tomcat</artifactId>
</exclusion>
```

**Root cause:** Spring Boot chooses its application type at start-up from the classpath
(`WebApplicationType.deduceFromClasspath`): if `jakarta.servlet.Servlet` and
`ConfigurableWebApplicationContext` are present it is `SERVLET`; if only the reactive classes are
present it is `REACTIVE`; otherwise it is `NONE`. `jakarta.servlet.Servlet` arrives via
`tomcat-embed-core`, inside `spring-boot-starter-tomcat`. Excluding the starter removes the class,
so the application type is `NONE`.

A `NONE` application runs its context, finds nothing holding the JVM open, closes the context and
exits — cleanly, with status `0`. The log even says `Started ExpenseApplication in 4.238 seconds`,
because it did start; there is simply no server and no port. The missing line is the one that
normally reads `Tomcat started on port 8080 (http)`.

**Fix:** delete the exclusion.

There is a legitimate use for it — excluding Tomcat in order to add Jetty or Undertow instead:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
```

The defect is the first half of that pair without the second.

**Why a fresher writes this:** exactly that — a half-finished container swap, or a copied snippet
from a Stack Overflow answer about switching to Undertow, or an attempt to "slim the jar down" by
removing things that looked unnecessary.

**How to recognise it in a real project:** an application that exits `0` immediately after
reporting that it started. Diff the start-up log against a known-good one and find the missing
line; then `mvn dependency:tree` for the container.

## Defect 4 — the Jackson JSR-310 module is excluded

**Where:** `pom.xml`, on `spring-boot-starter-web`.

```xml
<exclusion>
    <groupId>com.fasterxml.jackson.datatype</groupId>
    <artifactId>jackson-datatype-jsr310</artifactId>
</exclusion>
```

**Root cause:** Jackson has no built-in support for `java.time`. Spring Boot registers
`JavaTimeModule` automatically **if it is on the classpath**, which it normally is, transitively,
through the web starter. Excluded, every serialisation of a `LocalDate` fails:

```
InvalidDefinitionException: Java 8 date/time type `java.time.LocalDate` not supported by default:
  add Module "com.fasterxml.jackson.datatype:jackson-datatype-jsr310" to enable handling
```

Every endpoint that touches a date returns `500`; `/api/meta`, which has none, is unaffected. The
exception names the artifact, which makes this the easiest of the eight — provided you read the
server log rather than the HTTP response.

**Fix:** delete the exclusion. If you ever genuinely need to control it, add the dependency
explicitly rather than removing it and hoping.

**Why a fresher writes this:** exclusions get added while chasing a duplicate-class warning or a
CVE report, are usually copied from a search result, and are almost never removed afterwards. They
are also invisible in code review, because a POM diff of four extra lines reads like configuration
tidying.

**How to recognise it in a real project:** any "not supported by default" or `NoClassDefFoundError`
for a library you never removed. `mvn dependency:tree -Dincludes=<groupId>` tells you whether it is
in the tree; the POM tells you why it is not.

## Defect 5 — the wrong placeholder delimiter in a filtered resource

**Where:** `src/main/resources/application.properties`.

```properties
app.build-version=${project.version}
```

**Root cause:** Maven resource filtering and Spring's property resolver both use `${...}`, so
`spring-boot-starter-parent` reconfigures `maven-resources-plugin` to use `@` as its delimiter for
`application*.properties` and `application*.yml`. That way Maven expands `@project.version@` at build
time and leaves `${...}` alone for Spring at runtime.

Written as `${project.version}`, Maven ignores it and Spring tries to resolve it as a property named
`project.version`, which does not exist:

```
IllegalArgumentException: Could not resolve placeholder 'project.version' in value "${project.version}"
```

Because the value is read lazily by the controller, only `/api/meta` fails; everything else is fine.

**Fix:**

```properties
app.build-version=@project.version@
```

Then verify the substitution against the artefact, not the source:

```bash
unzip -p target/expense-reporting-1.0.0.jar BOOT-INF/classes/application.properties | grep version
```

The alternative, and arguably the better answer, is not to do this by hand at all: add the build-info
goal to the Boot plugin and inject `BuildProperties`, which gives you version, artifact, name and
build time without touching resource filtering.

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <executions>
        <execution><goals><goal>build-info</goal></goals></execution>
    </executions>
</plugin>
```

**Why a fresher writes this:** `${project.version}` is the correct syntax everywhere else in Maven —
in the POM itself, in every other filtered resource, in every tutorial. The `@` delimiter exists
only because of the collision with Spring, and it applies only to Boot's filtered property files.

**How to recognise it in a real project:** a placeholder that appears literally in output, or a
"Could not resolve placeholder" for a name that is obviously a build property. Always check the
filtered file inside the jar; `src/main/resources` cannot tell you whether filtering happened.

## Defect 6 — tests are skipped by configuration

**Where:** `pom.xml`, in the Surefire plugin.

```xml
<configuration>
    <skipTests>true</skipTests>
    ...
</configuration>
```

**Root cause:** exactly what it says. `mvn test`, `mvn package` and `mvn install` all print
`Tests are skipped.` and `BUILD SUCCESS`. Nothing is red, no report is written, and a build with no
tests is indistinguishable from a build whose tests all passed unless somebody reads the output.

**Fix:** delete the line. If you need to skip tests occasionally, use the command line
(`mvn package -DskipTests`) so that skipping is a deliberate act by a person, not the permanent
state of the project.

**Why a fresher writes this:** somebody needed a build out while a test was failing, put it in the
POM instead of on the command line, and it stayed. This is one of the most common ways a test suite
dies.

**How to recognise it in a real project:** read the build log for `Tests run:` and, if it is
missing, ask why. In CI, fail the build when the test count is zero — most reporting plugins can do
that, and it is the only reliable defence.

## Defect 7 — the Surefire include pattern does not match the test class

**Where:** `pom.xml`, in the same Surefire configuration.

```xml
<includes>
    <include>**/*Tests.java</include>
</includes>
```

The class is `ExpenseSummaryTest`.

**Root cause:** Surefire's defaults are `**/Test*.java`, `**/*Test.java`, `**/*Tests.java` and
`**/*TestCase.java`. Declaring `<includes>` **replaces** that list rather than adding to it, so only
`*Tests.java` counts and `ExpenseSummaryTest` is not a test as far as the build is concerned.

The output is the worst part: no "Tests are skipped", no "Tests run: 0", nothing at all, and
`BUILD SUCCESS`. `target/surefire-reports/` stays empty.

**Fix:** remove the `<includes>` block and let the defaults apply — they already cover every
sensible naming convention. If a project really does need a custom pattern, list every convention it
uses, and confirm with `Tests run:` that the number is what you expect.

**Why a fresher writes this:** somebody standardised on `FooTests` naming, added the pattern, and
did not notice the classes still called `FooTest`. It is also a classic outcome of copying a
`<configuration>` block from another project.

**How to recognise it in a real project:** a test count that is lower than the number of test
classes, or a build that runs no tests without saying so. Compare
`find src/test -name "*Test*.java" | wc -l` with the reported test-class count.

## Defect 8 — the discarded `BigDecimal` result

**Where:** `service/ExpenseService.java`.

```java
BigDecimal grandTotal = BigDecimal.ZERO;

for (Expense expense : expenses) {
    totalByCategory.merge(expense.getCategory(), expense.getAmount(), BigDecimal::add);
    grandTotal.add(expense.getAmount());
}
```

**Root cause:** `BigDecimal` is immutable. `add` computes a new value and returns it; it changes
nothing. The result is discarded, so `grandTotal` is still `BigDecimal.ZERO` when the summary is
built. The line above it uses `merge`, which *does* store its result, which is why the per-category
totals are correct and only the grand total is wrong — a contrast that points straight at the
difference between the two statements.

Java does not warn about an ignored return value. Some IDEs and static analysers do
(`ResultOfMethodCallIgnored`, SpotBugs `RV_RETURN_VALUE_IGNORED`), and this is a good argument for
turning them on.

**Fix:**

```java
grandTotal = grandTotal.add(expense.getAmount());
```

Or remove the possibility altogether:

```java
BigDecimal grandTotal = expenses.stream()
        .map(Expense::getAmount)
        .reduce(BigDecimal.ZERO, BigDecimal::add);
```

**Why a fresher writes this:** `total.add(x)` reads like `total += x`, and for `int` it would be
written that way. Every immutable type in Java has this trap — `String.trim()`, `String.replace()`,
`LocalDate.plusDays()`, `BigDecimal.setScale()` — and it always compiles.

**How to recognise it in a real project:** a value that stays at its initial value while everything
around it is right. When a total is exactly zero rather than merely wrong, suspect that the addition
never happened at all.

## Order of discovery

This project is a chain rather than a set. Each defect is invisible until the one before it is
fixed:

```
1 (no repackage)  →  2 (H2 scope)  →  3 (no servlet container)  →  4 (no JSR-310)  →  5 (placeholder)

6 (skipTests)  →  7 (include pattern)  →  8 (the real defect the tests would have caught)
```

The two chains are independent of each other, and the second one is the point of the project. A real
arithmetic defect sat in the code from the first commit; a test existed that caught it in five
seconds; the build was configured so that the test never ran, and the build was green the entire
time.

## Test baseline

With all eight defects present, `mvn test` prints **no test results at all** and reports
`BUILD SUCCESS` — first because of `skipTests`, then, once that is removed, because the include
pattern matches nothing.

Once the build defects (1–7) are fixed, the suite finally runs:
**5 tests run, 3 pass, 1 fails, 1 errors.**

| Test | Result | Defect |
|---|---|---|
| `anExpenseCanBeRecorded` | passes | — |
| `anExpenseWithoutAnAmountIsRejected` | passes | — |
| `theSummaryBreaksTheMonthDownByCategory` | passes | — |
| `theSummaryTotalsEveryExpenseInTheRange` | `expected 44660.0 but was 0.0` | 8 |
| `theServiceReportsWhichBuildItIs` | `Could not resolve placeholder 'project.version'` | 5 |

Note that defect 5 is caught by the test suite and defects 1–4 are not: the tests run on Maven's
test classpath, where the repackage step, the runtime scope, the servlet container and the packaged
jar are all irrelevant. A green test suite says nothing whatsoever about whether the artefact you
ship will start.
